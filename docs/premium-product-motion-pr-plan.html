demoframe roadmap

Premium Product Motion Upgrade

A PR-by-PR implementation plan for moving demoframe from clean framed UI output to staged, premium product motion while preserving deterministic rendering and strict anti-screenshot rules.

Recommended shape
Separate PRs, grouped into short stacks
First merge target
Wrapper shell plus layout QA
Main risk
Hardening the API before full-bleed composition is proven
Compatibility rule
No cinematic fields and output.motionBlur: off keep the direct capture path

How To Work This

Visual Architecture Stack

  1. Stage/canvas spike
  2. Wrapper shell plus layout QA
  3. Cinematic schema/runtime plumbing
  4. Visible premium slice
  5. Fieldwork A/B plus landscape proof

Rendering Stack

  1. output.motionBlur plumbing
  2. Motion registry plus shared sampling
  3. Encoder profiles and video budgets
  4. Real motion blur

Policy And Workflow Stack

  1. brief.intent and screenshot gates
  2. MCP, preview, docs, and agent workflow parity
  3. Generalized premium templates later

Do not combine the whole roadmap into one PR. The safe path is short stacks where each PR is reviewable by itself and gives the next PR a stable contract.

Depends on nothing. This is the first real merge candidate.
foundation stack: visual architecture

Objective

Make every scene render through the inert shell .df-scene > .df-scene-motion > .df-rail-motion > .df-rail, so cinematic motion can later write wrapper CSS variables without stomping existing inner transforms.

  2. Introduce a small helper such as sceneShell(index, railHtml) to avoid each scene inventing the wrapper.
  3. Convert every scene template to use the helper and keep existing .df-rail classes and slots intact.

Done When

Choreography-Only Motion Blur

Stacks after PR 2, PR 3, and PR 6. Do this after composition is worth blurring.
high risk rendering

Objective

Implement opt-in accumulation blur only for choreography windows from the registry. Never blur typing, changing counters, terminal output, or other text mutation.

Files To Touch

  • src/render/frames.ts
  • src/render/browser.ts
  • src/templates/motion/presets.ts
  • src/commands/render.ts
  • src/qa/report.ts

Implementation Steps

  1. Calculate eligible blur windows from the motion registry and active scene intervals.
  2. Clamp subframe sampling to the active scene interval. Allow crossfade sampling only inside the fade window.
  3. Implement raw RGBA accumulation using sharp decoded buffers. Use premultiplied alpha for transparent frames.
  4. Choose and test sRGB versus linear-light averaging on accent blobs, white cards, and text edges.
  5. Map quality to subframe count: draft 1, standard 3, high 8, with a global clamp and memory guard.
  6. Skip GIF for cinematic; allow GIF only for force with a warning.

Verification

  • Determinism test: render the same choreography frame twice and compare hashes.
  • Negative test: typing/counter frames do not blur text mutation.
  • Guard tests for pixel-count, subframe-count, and memory constraints.

Done When

  • Blur only appears during eligible choreography windows.
  • Transparent output uses correct premultiplied handling.
  • GIF skip/force semantics are visible in warnings/report semantics.

Automated PR Thread Workflow

Yes, this is possible as a coordinator workflow, but it should be built as a guarded orchestration loop, not as a blind auto-merge machine. The Codex app already exposes thread primitives for creating, reading, and steering background threads, plus heartbeat/cron automations for polling.

Available Building Blocks

  • list_projects and create_thread can create builder/reviewer threads in worktrees.
  • read_thread can inspect progress and extract the PR URL or blocker summary.
  • send_message_to_thread can feed review comments back to the builder thread.
  • fork_thread can create a related review thread from completed context.
  • automation_update can create a heartbeat or cron poller for long-running loops.
  • GitHub status, comments, approvals, and mergeability still need gh or another GitHub API path with credentials.

Important Limits

  • Codex can resolve review comments, but it cannot manufacture human approvals on protected branches.
  • Networked GitHub polling and merging require credentials and explicit command approval in restricted environments.
  • Each builder should work in its own branch/worktree to prevent cross-PR file conflicts.
  • The coordinator should stop on ambiguous merge conflicts, failing CI, or design approval gates.
1
Coordinator chooses the next plan item. Read a queue like the PR sequence above. Only start an item when its dependencies are merged or deliberately stacked on top of a known branch.
2
Builder thread implements the PR. Create a Codex thread in a new worktree with a branch like codex/premium-motion-wrapper-shell. Its prompt should include the specific plan card, acceptance criteria, branch target, expected tests, and the requirement to file or prepare a PR.
3
Coordinator waits for a PR URL or blocker. Poll the builder thread summary. If the builder is blocked on product/design input, stop and ask the user. If it produces a PR URL, record it as the active PR for that queue item.
4
Reviewer thread reviews the filed PR. Start a separate reviewer thread with a code-review prompt: inspect the diff, prioritize bugs and missing tests, avoid style churn, and return actionable findings. If GitHub access is available, it can also post comments; otherwise it returns comments to the coordinator.
5
Coordinator loops comments back to the builder. Send the review findings and any GitHub comments to the builder thread. The builder updates the branch, reruns tests, and reports the new commit SHA.
6
Approval loop checks external state. Poll GitHub for unresolved comments, requested changes, CI checks, mergeability, and required human approvals. Continue the builder/reviewer loop until the PR is clean or a human decision is required.
7
Coordinator merges and triggers the next item. Once checks and approvals pass, merge via the approved repository policy, archive or summarize the old builder/reviewer threads, then create the next builder thread from the updated base branch.

Coordinator Pseudocode

for item in roadmap:
  ensure item.dependencies are merged or choose an explicit stack base
  builder = create_thread(project worktree, prompt_for(item))
  wait until builder reports pr_url or blocker
  if blocker:
    ask user, then continue or stop

  reviewer = create_thread(project worktree, review_prompt(pr_url, item))
  while true:
    review = read_thread(reviewer)
    github = gh_pr_state(pr_url)

    if review.has_findings or github.has_requested_changes:
      send_message_to_thread(builder, comments_from(review, github))
      wait until builder reports updated_commit
      send_message_to_thread(reviewer, "Re-review updated PR")
      continue

    if github.ci_green and github.required_approvals_met and github.mergeable
       and github.unresolved_review_threads == 0:
      merge_pr(pr_url, match_head_commit: builder.reported_commit_sha)
      archive builder/reviewer threads
      break

    if github.needs_human or github.conflict:
      ask user for direction
      break

Scope: {objective}
Files likely involved: {files}
Acceptance criteria: {done_when}
Verification commands: {commands}

Keep the PR focused. Do not implement later roadmap items.

test results, and any risks.

Prompt Template For Reviewer Threads

Review PR {url} for demoframe.

Use a code-review stance. Prioritize bugs, regressions, missing tests, and roadmap scope creep.
Ground every finding in file/line references when possible.
Do not request broad refactors unrelated to this PR.
Return:
- blocking findings
- non-blocking findings
- test gaps
- approve/no-approve recommendation
